# Week 6 Member 2: Memory Integration Interface

## Purpose

This document specifies the versioned interface that another trusted system
can use to connect to the QA agent's persistent memory and session state. The
contract follows the MCP tool-description style but does not require a
specific network transport. Its identifier is
`qa-agent.memory-interface/v1`.

The implementation source is `src/integration/mcp_interface.py`. Persistent
storage and the session lifecycle are implemented in `src/memory/store.py`.

## Capabilities

| Capability | Input summary | Output summary | Required permission | Effect |
| --- | --- | --- | --- | --- |
| `qa_memory.get_record` | Namespace and record ID | One record or `null` | `memory:read` | Read only |
| `qa_memory.list_records` | Namespace and bounded limit | Records and truncation flag | `memory:read` | Read only |
| `qa_memory.store_record` | Namespace, record ID, record, expiry, expected revision | Stored record envelope | `memory:write` | Mutating |
| `qa_memory.delete_record` | Namespace, record ID, expected revision | Deletion result | `memory:delete` | Mutating |
| `qa_state.get_session` | Session ID | Session state or `null` | `state:read` | Read only |

The exact JSON Schemas are generated by `describe_interface()`. Every input
and output is a closed object, so undeclared top-level fields are rejected by
an adapter that follows the contract.

## Connection Flow

1. The transport authenticates the caller.
2. The adapter maps the authenticated identity to explicit permission scopes.
3. `require_capability()` verifies the required scope.
4. Write requests pass through Member 3's memory API, which validates Member
   1's record schema and applies the data-handling policy.
5. The memory API calls `MemoryStore` with an expected revision.
6. The adapter returns only the declared output fields and records an audit
   event.

## Concurrency and State

Creates omit an existing revision by setting `expected_revision` to `null`.
Updates provide the revision returned by the previous read. A stale update is
rejected instead of silently overwriting another writer's change.

External systems can read session state but cannot change it. Only the trusted
agent runtime persists a legal transition. The allowed phases are `created`,
`running`, `awaiting_approval`, `completed`, `halted`, and `failed`.

## Security Boundary

- Memory is advisory context. It is never proof of human approval.
- No interface capability resumes a session, dispatches a tool, or executes an
  action.
- `pending_approval_id` means only that a decision is pending. It does not
  contain or imply an approval decision.
- A write is accepted only after record-schema and data-policy validation.
- Deletion requires the separate `memory:delete` scope so the retention job can
  run without receiving general write authority.
- Project data must be encrypted in transit and capability calls must be
  audited by the deployment adapter.

## Team Integration Points

| Owner | Integration point |
| --- | --- |
| Member 1 | Defines the memory record in `src/memory/schema.py`. |
| Member 2 | Provides `MemoryStore`, `SessionState`, and this interface contract. |
| Member 3 | Validates and reads or writes records through `src/memory/api.py`. |
| Member 4 | Tests that memory cannot bypass the approval gate. |
| Member 5 | Uses expiry metadata and revision-safe deletion in `src/memory/retention.py`. |

This separation lets each member complete their assigned component without
duplicating another member's policy or security work.
